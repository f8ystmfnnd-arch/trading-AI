# Development Rules

## 기본 원칙

이 프로젝트는 `BTC Market Regime & Risk Guard AI`이다. 가격 예측보다 리스크 관리가 우선이며, 방향성 예측은 보조 신호다.

개발 중에는 데이터 무결성, 시간 순서, 백테스트 신뢰성을 최우선으로 둔다.

## 개발 환경과 기기 역할

프로젝트의 로컬 개발 기준 환경은 **데스크탑 PC**다.

### 데스크탑: 주 개발 및 실행 환경

데스크탑을 다음 작업의 기준 환경으로 사용한다.

- 대용량 Bybit 원본 데이터 보관 및 갱신
- 전체 feature / target 재생성
- 모델 학습 및 재학습
- 전체 기간 백테스트와 walk-forward 검증
- 장시간 실행되는 데이터 수집
- 실시간 추론 프로세스와 Streamlit 대시보드 운용
- 모델·대용량 실험 산출물의 로컬 보관
- 성능이나 결과가 실제 로컬 데이터에 의존하는 최종 검증

데스크탑의 로컬 데이터와 모델은 GitHub에 전부 올리는 것을 전제로 하지 않는다. GitHub에는 재현에 필요한 소스코드, 설정, 작은 검증 자료와 문서를 우선 저장한다.

### 노트북: 보조 개발 환경

노트북은 이동 중에도 프로젝트를 이어갈 수 있는 보조 환경으로 사용한다.

주 용도는 다음과 같다.

- GitHub 저장소 확인과 코드 리뷰
- 문서 작성 및 정리
- 작은 코드 수정
- 작은 synthetic fixture 기반 테스트
- README, roadmap, architecture, experiment 기록 갱신
- GitHub / Codex / Work를 이용한 저장소 분석과 개발 계획 정리
- 데스크탑에서 수행할 다음 실험이나 구현 작업 준비

노트북에서는 대용량 원본 데이터를 복제하거나 전체 모델 학습·장시간 백테스트를 기본 작업으로 삼지 않는다. 필요한 경우 별도 환경을 준비한 뒤 명시적으로 실행한다.

노트북에서 코드가 정상 동작했다고 해서 데스크탑의 실제 데이터·모델 환경에서 검증된 것으로 간주하지 않는다.

### Cloud / Work 사용 원칙

Cloud 또는 Work 환경은 저장소 분석, 코드·문서 수정, 테스트 가능한 범위의 검증에 사용할 수 있다.

- Cloud는 데스크탑의 uncommitted 로컬 파일이나 Git에 올라가지 않은 대용량 데이터가 있다고 가정하지 않는다.
- Cloud에서 판단해야 하는 변경은 먼저 GitHub에 반영되어 있어야 한다.
- 실제 대용량 데이터, 모델, 장시간 실행이 필요한 최종 검증은 데스크탑에서 수행한다.
- Cloud에서 확인하지 못한 로컬 실행 결과를 성공했다고 기록하지 않는다.

## 여러 기기에서 Git 사용

GitHub를 **소스코드와 프로젝트 문서의 공통 기준점**으로 사용한다.

한 기기에서 작업을 시작하기 전에:

```powershell
git status
git pull --ff-only
```

작업이 끝나면 적절한 테스트를 수행한 뒤 변경 내용을 확인한다.

```powershell
git status
git diff
```

의미 있는 작업 단위가 끝났다면 commit하고 GitHub에 push한다. 다른 기기에서 이어서 작업할 때는 반드시 먼저 최신 변경을 pull한다.

원칙:

- 같은 브랜치의 서로 다른 기기에서 uncommitted 작업을 동시에 만들지 않는다.
- 데스크탑에서 작업 중인 변경을 노트북에서 이어서 수정하려면 먼저 commit/push한다.
- 노트북에서 수정한 코드도 데스크탑에서 이어서 작업하기 전에 commit/push한다.
- 동시에 독립적인 작업을 해야 한다면 별도 branch를 사용한다.
- 대용량 데이터, 모델, 로그, 임시 산출물을 기기 간 동기화하기 위해 Git을 사용하지 않는다.
- GitHub의 코드와 문서는 공통 기준점이지만, 실제 운용 데이터와 모델의 기준 로컬 환경은 데스크탑이다.

## Lookahead Bias 방지

미래 정보를 현재 피처나 의사결정에 섞으면 안 된다.

- 현재 시점의 피처는 현재까지 확인 가능한 데이터만 사용한다.
- 타깃 생성 시 미래 수익률이나 미래 변동성은 label로만 사용한다.
- rolling feature는 미래 행을 참조하지 않는다.
- 리샘플 데이터는 candle close 이후에만 사용 가능한 것으로 간주한다.
- 뉴스 데이터는 실제 공개 시각 이후에만 사용할 수 있다.

## Time-Series Split

검증은 시간 순서를 지켜야 한다.

- train, validation, test는 시간 순서대로 나눈다.
- 과거 데이터로 학습하고 미래 데이터로 검증한다.
- `shuffle=True`는 기본적으로 사용하지 않는다.
- cross validation이 필요하면 time-series 전용 방식을 사용한다.
- walk-forward 검증을 우선 고려한다.

## 백테스트 원칙

- 수수료와 거래 횟수를 반드시 고려한다.
- buy and hold 대비 수익률만 보지 않는다.
- MDD 감소, 고변동 구간 회피, 급락 구간 회피를 함께 본다.
- 포지션 축소가 실제로 위험 감소에 기여했는지 확인한다.
- threshold 튜닝은 test 데이터에 과적합하지 않도록 분리한다.

## 데이터와 산출물 관리

대용량 데이터와 생성 산출물은 GitHub에 올리지 않는 방향으로 관리한다.

- `data/raw/` 파일을 임의로 삭제하지 않는다.
- `data/processed/` 파일을 덮어쓰기 전에 입력과 생성 조건을 확인한다.
- `model/` 또는 `models/`의 모델 파일을 함부로 삭제하지 않는다.
- `experiments/`의 대용량 결과 파일을 임의로 수정하지 않는다.
- 중요한 실험 결론은 작은 Markdown 요약으로 남긴다.

## Git 작업 원칙

- 사용자가 명시적으로 요청하지 않으면 `commit`하지 않는다.
- 사용자가 명시적으로 요청하지 않으면 `push`하지 않는다.
- 사용자가 명시적으로 요청하지 않으면 PR을 만들지 않는다.
- 작업 전후로 변경 파일 목록을 확인한다.
- 사용자 변경으로 보이는 파일은 되돌리지 않는다.

## 뉴스 데이터 사용 원칙

뉴스는 매수/매도 신호가 아니다.

- 긍정 뉴스면 매수, 부정 뉴스면 매도 같은 단순 로직을 사용하지 않는다.
- 뉴스는 변동성, 불확실성, 이벤트 위험도 판단에 사용한다.
- 뉴스 점수는 차트 기반 리스크 점수와 결합해 최종 risk score에 반영한다.
- 뉴스의 영향 시간대를 short / medium / long으로 구분한다.

## Mode 분리 원칙

`Day Trading Mode`와 `Swing Trading Mode`는 목적과 시간축이 다르므로 분리해서 설계한다.

- `Day Trading Mode`: 1m / 5m / 15m / 1h 중심, 신규 진입 위험과 단기 변동성 판단
- `Swing Trading Mode`: 15m / 1h / 4h / 1d 중심, 시장 국면과 포지션 유지 위험 판단

## 수집 기능 우선순위

`collect_bybit_1m.py`는 먼저 다음 기능을 안정화한다.

- `--days`
- `--update`

`--watch`는 실시간 대시보드 단계에서 다룬다.
